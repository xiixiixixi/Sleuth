Sleuth Search Loop Spec

这是一个 plugin 级别的搜索任务运行规范。它不是复杂工作流系统，也不是搜索技巧百科。 它定义需要调研闭环的搜索任务中少数不可跳过的动作：先定问题、拓宽搜索空间、多角度取证、回来后审查、必要时补一轮、最后交付并留痕。

Spec Draft Plugin-level 伪代码级设计 中文为主，英文附解释
一句话目标：让模型不要在 subagent 返回后“合并即结束”，而是通过轻量 Review（审查）和 Patch（补查）闭环，判断当前答案是否足够。

1. 范围与非目标

目标

  • 定义通用搜索任务的做事方式，而不是列出所有搜索技巧。
  • 让调研型任务有可执行的闭环：Frame → Expand → Search → Review → Patch → Deliver。
  • 明确 Main Agent（主 Agent）和 Subagent（子 Agent）的职责边界。
  • 减少上下文变长后忘记自查、忘记补证、忘记留痕的问题。
  • 提供可直接落地到 SKILL.md、references/ 下短文档和少量脚本的规范。

非目标

  • 不做完整 workflow engine（工作流引擎）。
  • 不要求每个阶段都由 subagent 处理。
  • 不维护巨大的搜索渠道大全。
  • 不要求每个简单问题都创建 session 或状态文件。
  • 不替代模型判断；只在关键节点设置门槛。
设计取舍：Plugin 应该像“研究质量护栏”，不是“研究管理系统”。如果机制过重，模型会绕开或执行成本过高；如果机制太软，调研任务会提前结束。

2. 设计原则

  1. Main Agent owns the thread（主 Agent 负责主线）。主 Agent 做问题拆解、缺口判断、是否补一轮、最终交付。Subagent 只收集证据和线索。
  2. Subagent is a probe, not a project owner（子 Agent 是探针，不是项目负责人）。它可以追一跳新线索，但不能无限扩展主线。
  3. Review before final（交付前必须审查）。Subagent 回来后，主 Agent 必须问“够了吗、哪里薄、哪里可能错”，不能直接 final。
  4. Emphasize blind spots（强调盲区）。不要教模型所有渠道；重点提醒模型容易漏的：反证、负面、身份映射、真实用户反馈、最新性。
  5. State can be lightweight（状态可以轻量）。不需要复杂数据库；进入 Research Loop 的任务至少保留 questions、expansion、findings、gaps、red flags。
  6. Artifacts should steer behavior（产物要能驱动下一步）。产物不是为了好看，而是让模型知道是否补查、补查什么。

3. 两级路由

复杂度让模型自己判断，但 plugin 只要求它做一个二选一决定：直接回答，还是进入 Research Loop（调研闭环）。不要设计三档、五档或“标准/复杂/深度”这样的中间等级；中间等级会增加执行歧义，后期上下文变长时最先被遗忘。

路由 进入条件 执行要求 是否需要 subagent
Direct Answer
直接回答		 单一事实、低风险、用户只要快速确认，或一两个可靠来源即可回答。 可以搜索或打开原文，但不创建状态、不派 subagent、不进入完整闭环。最终回答给出必要来源和不确定性。 不需要。
Research Loop
调研闭环		 开放问题、多个来源才能回答、可能影响决策、需要比较/判断/风险识别，或存在别名、身份映射、时效、负面信息等盲区。 完整 Search Loop，必须 Review，必要时 Patch。 只在可并行独立取证时使用。

Research Loop 触发信号

只要出现以下任一信号，默认进入 Research Loop，除非用户明确要求快速简答：

  • 用户使用“深度调研、全面、竞品、市场、公司、产品线、融资、团队、客户案例、风险、负面、最新”等词。
  • 需要多个渠道才能回答，例如官网 + 第三方 + 社区 + 新闻。
  • 一个结论可能影响决策，例如采购、投资、技术选型、公开发布。
  • 存在明显别名、品牌、域名、公司主体或语言差异。
关键约束：复杂度可以在 Research Loop 内部体现为搜索轮次、subagent 数量和 patch 成本，但对 skill 来说只保留两个入口。模型不需要先纠结“标准还是复杂”，只需要判断“是否必须走闭环”。

4. 主流程

Direct Answer 直接回答不进入下面闭环。只有路由到 Research Loop 的任务，才执行这套轻量闭环，而不是重型状态机：

Recall 历史召回
→ Frame 定义问题
→ Expand 拓宽搜索空间
→ Search / Probe 搜索或派探针
→ Review 审查覆盖和可信度
→ Patch 针对缺口补一轮
→ Deliver 交付和留痕
核心差异：Subagent 回来后不是进入 Deliver，而是进入 Review。Review 发现缺口时进入 Patch，再回到 Review。

4.1 主流程伪代码

function runSearchTask(userRequest):
  route = classifyRoute(userRequest)  # "direct" | "research_loop"

  if route == "direct":
    result = answerDirectlyOrWithMinimalSources(userRequest)
    return deliverDirectAnswer(result)

  recallResult = recall(userRequest)
  frame = buildFrame(userRequest, recallResult)
  expansion = expandSearchSpace(frame)

  findings = []
  round = 1

  while round <= MAX_ROUNDS:
    plan = chooseSearchPlan(frame, expansion, findings)

    if plan.hasIndependentAngles:
      findings += runSubagents(plan.angles)
    else:
      findings += mainAgentSearch(plan)

    review = reviewFindings(frame, expansion, findings)

    if review.isEnough:
      break

    patchTasks = makePatchTasks(review.gaps)
    findings += runPatchSearch(patchTasks)
    round += 1

  finalReview = finalCheck(frame, findings)

  if finalReview.hasCriticalGap:
    discloseGapOrPatchAgain(finalReview)

  return deliverAnswer(findings, finalReview)

6. Search Expansion（搜索拓宽）

Search Expansion 不只是别名和渠道表。它是调研型搜索前的一次“空间展开”。Skill 里不需要列出所有渠道，只需要强制模型从六个方向想一遍。

6.1 Entity Expansion（实体扩展）

别名、品牌、域名、产品线、公司主体、创始人、旧名称、缩写、母公司/子公司。

例：Shulex、数里、VOC AI、Solvea、joinshulex.com、voc.ai。

6.2 Question Expansion（问题扩展）

用户问 A，但回答 A 可能必须先回答 B/C/D。

例：问“产品怎么样”，需要同时查定位、客户、价格、限制、用户反馈。

6.3 Source Expansion（来源扩展）

官方、一手、用户反馈、第三方、社区、监管/注册、代码/文档、视频/访谈。

不是全量渠道大全，而是选择与任务相关的来源类型。

6.4 Perspective Expansion（视角扩展）

官方视角、用户视角、竞品视角、投资人视角、技术实现视角、采购视角。

6.5 Contradiction Expansion（反证扩展）

限制、投诉、失败案例、负面评价、价格争议、替代方案、过期信息。

这是模型最容易漏的部分，应在 skill 中重点强调。

6.6 Freshness Expansion（时效扩展）

最新公告、最近版本、最近新闻、页面更新时间、旧资料复核。

6.7 扩展伪代码

function expandSearchSpace(frame):
  expansion.entities = inferAliasesAndRelatedEntities(frame)
  expansion.questions = deriveHiddenQuestions(frame)
  expansion.sources = chooseRelevantSourceTypes(frame)
  expansion.perspectives = choosePerspectives(frame)
  expansion.contradictions = chooseContradictionSearches(frame)
  expansion.freshness = decideFreshnessChecks(frame)

  return expansion
Plugin 重点：不需要告诉模型所有渠道。要提醒它最容易漏的：反证、身份映射、用户真实反馈、最新性、站内深挖。

7. Subagent 协议

Subagent 的正确定位是 Probe（探针）或 Evidence Collector（证据收集者），不是阶段负责人。

7.1 分配原则

  • 只把可并行、边界清晰的角度派给 subagent。
  • 不要让 subagent 做 Orient、最终判断或最终交付。
  • 每个 subagent 应有指定 source class（来源类型）或 perspective（视角）。
  • subagent 发现新线索时可以追一跳，但不能无限扩展主线。

7.2 子 Agent 发现新线索怎么办

情况 允许动作 返回给主 Agent 的字段
线索明显关键，且很快可验证 允许追一跳。 findings 增加验证结果。
线索可能重要，但会展开新分支 不扩展，记录为 lead。 leads。
线索可能推翻主线 标记 red flag，优先返回。 red_flags。
当前角度无法查清 记录缺口，不伪造结论。 gaps。

7.3 Subagent 输出协议

{
  "angle": "第三方用户评价 / 用户真实反馈",
  "scope": "只查公开评论、社区讨论、marketplace reviews",
  "findings": [
    {
      "claim": "用户主要称赞安装简单",
      "sources": ["https://..."],
      "confidence": "medium"
    }
  ],
  "sources": [
    {
      "url": "https://...",
      "type": "marketplace_review",
      "why_relevant": "真实用户反馈"
    }
  ],
  "leads": [
    "多个评论提到 pricing 限制，建议主 Agent 补查定价页"
  ],
  "gaps": [
    "没有找到足够多企业客户评价"
  ],
  "red_flags": [
    "一个来源声称该产品已更名，需主线复核"
  ]
}
硬规则：Subagent 不能 finish 主 session，不能写最终答案，不能把自己的局部结论包装成全局结论。

8. Review 与 Patch

这是本 spec 最重要的部分。调研任务真正容易失败的点，不是不会搜，而是“资料看起来够了就结束”。

8.1 Review 输入

  • 原始用户问题。
  • Frame 阶段的问题清单。
  • Expand 阶段的搜索拓宽结果。
  • 主 Agent 和 subagents 的 findings、sources、leads、gaps、red_flags。

8.2 Review 输出

{
  "coverage": {
    "answered_questions": ["Q1", "Q2"],
    "unanswered_questions": ["Q3"],
    "covered_perspectives": ["official", "user_reviews"],
    "missing_perspectives": ["negative", "freshness"]
  },
  "weak_claims": [
    "定价结论只有官方来源，没有第三方验证"
  ],
  "red_flags": [
    "品牌关系存在不一致说法"
  ],
  "is_enough": false,
  "patch_tasks": [
    "查 negative / complaint / limitation",
    "复核品牌更名和公司主体"
  ]
}

8.3 Patch 规则

  • Patch 只针对缺口，不重复第一轮泛搜。
  • Patch 可以由主 Agent 自己做，也可以派一个小 subagent。
  • Patch 后必须重新 Review。
  • 最多补几轮由任务成本决定；如果仍有缺口，最终交付必须披露。

8.4 Final 前检查

function canDeliver(review):
  if review.red_flags contains critical item:
    return false
  if review.unanswered_questions contains user-critical question:
    return false
  if review.missing_perspectives contains required perspective:
    return false
  return true

10. Skill 合约

下面是建议写进 SKILL.md 的核心规则。它应该短，且可执行。

10.1 可直接进入 SKILL.md 的规则

Research Loop 任务必须遵循 Search Loop：
1. Recall：先查历史。
2. Frame：写出 3-8 个要回答的问题。
3. Expand：从实体、问题、来源、视角、反证、时效六个方向拓宽搜索空间。
4. Search：主 Agent 搜主线；只有可并行独立取证时才派 subagent。
5. Review：subagent 或搜索结果回来后，必须检查覆盖、弱证据、缺口和 red flags。
6. Patch：如果 Review 发现关键缺口，先补一轮，再交付。
7. Deliver：最终答案必须说明来源、低置信度和未覆盖范围。

10.2 可直接进入 subagent-guide 的规则

你是 Probe（探针），不是最终报告作者。
你的输出必须包含：
- findings：已验证发现
- sources：来源 URL
- leads：值得主 Agent 追的新线索
- gaps：没查完的缺口
- red_flags：可能推翻主线的信号

你可以追一跳关键线索，但不能无限扩展任务。
你不能 finish 主 session，不能写最终答案。

10.3 Browser Runtime Contract（浏览器运行合约）

凡是调用 agent-browser：
1. 必须连接用户日常 Chrome（带登录态、Cookie、书签、历史）。
2. 命令必须带 --auto-connect --session <name>。
3. 主 Agent 用 ${SID}-main；subagent 用主 Agent 分配的 ${BROWSER_SESSION}。
4. 禁止裸跑 agent-browser open/click/snapshot；裸跑会启动独立 Chrome for Testing，丢失登录态。
5. Chrome 必须在启动时带 --remote-debugging-port=9222；已运行的 Chrome 不会接收后续 open -a 传入的新参数。
6. 如果 Chrome CDP 不可用，先执行 check-deps：关闭/终止现有 Chrome，再用正确参数重启。
7. 不能直接降级到 curl/WebFetch 绕过登录态页面。
8. 不操作用户已有 tab；所有操作在隔离 session 的新 tab 中完成。

11. 开发落地

落地时不要把每个阶段都拆成一个 md，也不要只写三个粗文档。正确粒度是：把模型容易忘、容易做错、需要强制回看的部分拆出来；把模型天然会做的普通搜索技巧留给模型能力。

推荐结构：SKILL.md 只放入口规则和硬门禁；references/ 放可按需打开的短规范；脚本只负责召回、状态和留痕，不负责替模型做判断。

11.2 文件职责边界

SKILL.md 应该写什么

  • 只保留两级路由：Direct Answer 与 Research Loop。
  • Research Loop 的不可跳过动作：Recall、Frame、Expand、Search、Review、Patch、Deliver。
  • Subagent 只作为 probe，不能 finish 主 session。
  • Final 前必须做 Review；缺口关键时必须 Patch 或披露。

references/ 应该写什么

  • 模型容易忘的流程锚点。
  • 模型容易忽略的搜索盲区。
  • Subagent 返回格式和边界。
  • Review/Patch 的检查清单。
不需要单独成文档的内容：普通搜索语法、常见搜索引擎用法、每个网站怎么搜、完整渠道大全。模型通常知道这些；skill 应该强调它容易漏掉的判断节点和质量门槛。

11.3 Phase A：先落地文档

  1. 修改 sleuth/skills/sleuth/SKILL.md：压缩成入口合约，只保留两级路由和硬门禁。
  2. 新增或重写 sleuth/references/search-loop.md：作为完整闭环的短规范。
  3. 新增或重写 sleuth/references/search-expansion.md：只写盲区拓宽，不做渠道百科。
  4. 检查 sleuth/references/tool-guide.md：把登录态 Chrome、--auto-connect --session、CDP 缺失时先关闭再重启、禁止裸 agent-browser 写成第一屏硬规则。
  5. 修改 sleuth/references/subagent-guide.md：强化 probe 协议，删除任何“完成/最终交付”的暗示。
  6. 新增 sleuth/references/review-checklist.md：把 Review/Patch 从“建议”变成 final 前检查门槛。

11.4 Phase B：再补轻量状态

如果仅靠指令仍不稳定，再新增 search-state.mjs。它不做复杂工作流，只做状态读写和回看提醒。

node search-state.mjs init --sid "$SID" --goal "..."
node search-state.mjs update --sid "$SID" --section expansion --json '{...}'
node search-state.mjs append --sid "$SID" --section findings --json '{...}'
node search-state.mjs review --sid "$SID"
node search-state.mjs show --sid "$SID"

11.5 不建议第一版做的事

  • 不要做完整 DAG 调度系统。
  • 不要把每个阶段都工具化。
  • 不要强制所有 Research Loop 任务都跑 audit agent。
  • 不要维护庞大的渠道矩阵。
  • 不要引入多级复杂度枚举；两级路由足够驱动 plugin 行为。

12. 验收场景

场景 期望行为
公司/产品调研 先 Frame，再 Expand，至少包含身份映射、用户反馈、反证和时效检查中的相关项。
Subagent 返回很多材料 主 Agent 不直接 final，先 Review，列出 missing perspectives 和 weak claims。
Subagent 发现新产品线 记录为 lead 或 red_flag，由主 Agent 决定是否 Patch。
只找到官方来源 Review 标记单一来源风险，决定补查第三方/用户反馈，或最终披露限制。
长上下文任务恢复 先读 Search State 或前序产物，再继续 Review/Patch，不从记忆猜进度。

术语表

术语 中文解释
Search Loop搜索运行闭环：Frame、Expand、Search、Review、Patch、Deliver。
Frame定义问题：把用户需求拆成可验证问题。
Search Expansion搜索拓宽：从实体、问题、来源、视角、反证、时效扩展搜索空间。
Probe探针：子 Agent 的角色，只负责独立角度取证。
Review审查：判断材料是否足够、哪里薄、哪里可能错。
Patch补查：针对缺口补一轮搜索。
Lead线索：值得追但未验证或超出当前子任务范围的信息。
Red Flag危险信号：可能推翻主线或显著改变结论的发现。

附录：可直接复制的 prompt 片段

Research Loop 启动片段

这是 Research Loop 搜索任务。不要直接开始泛搜。
先输出：
1. Frame：3-8 个要回答的问题
2. Search Expansion：实体、问题、来源、视角、反证、时效
3. Search Plan：哪些由主 Agent 搜，哪些可派 subagent

Subagent 只作为 probe，不负责最终答案。

Subagent 任务片段

你是 probe，不是最终报告作者。
你的角度是：{angle}
你的来源范围是：{source_scope}

返回必须包含：
- findings
- sources
- leads
- gaps
- red_flags

可以追一跳关键线索，但不能无限扩展任务。
不要 finish 主 session。

Review 片段

现在不要直接 final。
先做 Review：
1. 哪些问题已回答？
2. 哪些问题没回答？
3. 哪些结论只有单一来源？
4. 哪些容易漏的视角没覆盖？
5. 有没有 red flags？
6. 是否需要 Patch？如果需要，列出 patch tasks。

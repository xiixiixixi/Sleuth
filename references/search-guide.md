# 搜索方法论

主 Agent 和子 Agent 共用同一套搜索判断。本文只回答一件事：**怎么在最少仪式下，找到足够可信的证据。**

## 何时搜 vs 不搜（明文规则，不靠模型瞎判断）

**必搜**：
- 时效信息（新闻、价格、比分、版本号、融资）
- 陌生专有名词——产品、公司、人物、事件（unrecognized capitalized word 几乎肯定是名字，不是普通名词）
- "现任 X"、"最新 Y"、"今天 Z"
- 用户引用 URL（要 fetch，不是 search）
- 高风险话题（金融/医疗/法律）必须多源核对

**必不搜**：
- 既定事实（数学定理、历史确凿日期）
- 用户已经在对话里提供过的内容
- 创意写作、闲聊、问候
- 已去世人物的身份查询（除非问"最近做过什么"）

**关键判断**：用户的问题是不是依赖"可能已经变了"的信息？是 → 搜。不是 → 直答。

## 七个判断动作

```
目标 → 来源拓扑 → 查询 → 观察 → 怀疑 → 换路 → 停止
```

### 目标

先写清：
- 要证明什么、找到什么、交付什么
- 什么叫 enough（多少源、什么类型）
- 哪些事实必须回到原始来源

没有目标，搜索词会越搜越散。

### 来源拓扑

先问"这个事实通常存在于哪类来源"，再问"该搜什么词"。

| 信息类型 | 常见高价值来源 |
|----------|----------------|
| 公司基本面 | 官网 About、官方新闻、LinkedIn、投资方公告 |
| 产品能力 | Docs、API、Product 页面、Changelog、Demo |
| 定价 | Pricing、Help Center、FAQ、Sales docs |
| 客户案例 | Customers、Case Study、Marketplace、第三方测评 |
| 安全合规 | Security、Trust Center、SOC2/GDPR 页面 |
| 真实反馈 | G2、Capterra、Reddit、YouTube、社区讨论 |

## 查询改写规则

**起步**：1-6 词短查询优先。先 broad（1-2 词），不够再 narrow。

**禁止**（除非用户明确要求）：
- 用 `-` 排除操作符
- 用 `site:` 限定
- 用引号强制精确匹配
- 把长句塞进搜索框（query 不是 prompt）

**多查询并行**：仅在问题需要按"含义不同"维度分解时（比如"对比 A 和 B 的定价"），才同时发多个 query。否则单查询优先。

**多语言**：用户用中文问，发中文 + 英文两个 query。

**中间反哺**：每轮搜完做 gap analysis——"还缺什么？" → LLM 生成补漏 query → 执行。这是 Perplexity Deep Research 和 open_deep_research 的核心模式。

**警告**：最近 2 次搜索返回类似信息 → 不再发相似 query，不会产生新结果。

## 何时立即停（硬规则）

满足任一就停，不要为完美继续搜：

1. **能全面回答用户问题**——核心事实都有源支撑
2. **已有 3+ 个相关的独立来源**——不是 3 个转载同一个源
3. **最近 2 次搜索返回类似信息**——再搜也是冗余

不能停的情况：
- 关键结论只有单一脆弱来源
- 存在明显冲突但还没说明
- 重要数字没有时间戳或来源
- 你只是"流程做完了"，但问题还没真正回答

## 观察：每一步都读反馈

你看到的不是"成功/失败"，而是下一步的提示：

- 搜索结果暴露了别名、子品牌、旧品牌名
- 页面暴露了更直接的 docs / pricing / security 入口
- 结果过旧，说明要加时间线或 freshness 判断
- 一个站点全是营销话术，说明要换来源类型

观察完再决定下一步；不要机械照原计划走。

## 怀疑：主动找自己可能错在哪

每轮至少问：

- 我现在拿到的是原始来源，还是摘要、转载、营销页？
- 这个数字有时间戳吗？有没有旧数据冲突？
- 我是不是只看了排名靠前的结果？
- 我是不是把公司名、产品名、域名混为一谈？
- 我是不是在同一条失败路径上重复尝试？

## 换路：当前路径没产出就换来源类型

以下信号说明该换路：

- 连续两轮没有新信息
- 同一类页面互相复读
- 搜索结果都在引用同一个源
- 当前路径只剩 SEO 文、摘要或失真的 reader 输出
- 页面需要交互/展开/登录/真实状态判断，而你还在用静态 reader

常见换路方式：

- 从搜索结果切到官网、docs、pricing、security、changelog
- 从 reader 切到浏览器 DOM / eval
- 从 Google / Bing 切到 `site:`、YouTube、App Marketplace、GitHub
- 从公网搜索切到本地历史、书签、组织入口

## 证据：写结论时必须知道凭什么

关键结论至少记录：

```
Claim → Evidence → Source → Time → Confidence → Conflict
```

最少要求：

- **有 URL，且 URL 不可缺**——没有来源 URL 的结论不算证据
- 能看出来源类型（official / docs / review / community / news）
- 涉及价格、融资、版本、团队等会变的事实时，要有时间戳
- 遇到冲突不要抹平，明确写出冲突和判断依据
- 图片分析的结论标注"视觉分析"，附原始图片 URL

### 证据层级

| 层级 | 常见来源 | 用法 |
|------|----------|------|
| **Tier 1** | 官方文档、官方博客、官方定价页、监管或权威原始文件（.gov / SEC / 同行评议） | 核心事实首选 |
| **Tier 2** | 行业分析、第三方深度评测、GitHub README / issues、成熟评论站 | 补强、对照、寻找反证 |
| **Tier 3** | 搜索摘要、SEO 文、未署名新闻稿、单条论坛评论 | 用于发现线索，**不单独支撑核心结论** |

**特别警惕**：SEO-heavy 主题（产品推荐、评测榜单）、阴谋论常涉主题——保持怀疑，多源核对。

## 冲突处理

- 同一事实 2+ 源冲突 → **再搜一次**确认，不要凭印象选边
- 争议性话题 → 搜"distribution of sources representing all parties"——刻意找各方立场
- 找不到清晰答案 → 诚实告诉用户"源之间存在分歧"，列出各方说法
- 时效冲突 → 优先取最近 30 天内的源，但明示旧源说什么
- 合成前做 cross-source validation：列出每个 claim 的 support count，support < 2 的标 confidence low

## 引用纪律

- **每个核心结论必须内联来源 URL**：`[结论](https://来源URL)`。不要只在末尾堆 sources 列表。
- 单源最多 **1 句直接引用**，且不超过 15 词。超过就 paraphrase。
- 默认 paraphrase，不直引。
- 不要用 bullet/numbered list 重现原文章结构（防止 copyright 替代）。
- 涉及高风险话题：用"according to X"，不用"权威认证"。

## 常见战术

### 1. 实体扩展

公司名 ≠ 产品名 ≠ 域名 ≠ 法人主体。中英文名、旧品牌名、母子公司关系都可能影响检索结果。

### 2. 反证搜索

不要只搜正面材料。常用反证关键词：`complaint` / `limitation` / `vs alternative` / `lawsuit` / `shutdown` / `pricing controversy`。

### 3. 站内深挖

找到高价值站点后优先深挖：docs / pricing / help / faq / changelog / security / customers。

### 4. 视频与演示

创始人访谈、产品演示、用户教程常在视频里。YouTube 站内搜或搜索引擎找 YouTube 结果。字幕/转录按 `tool-guide.md` 的特殊内容类型处理。

## 遇到障碍时

| 障碍 | 处理 |
|------|------|
| 登录弹窗 | 先判断是否还能读到所需信息；不行就让用户登 |
| 付费墙 | 只用可见内容，找公开替代来源，**不绕过** |
| CAPTCHA / anti-bot | 暂停该路径，换来源类型或换入口 |
| 429 / 限流 | 降频、换站、换方法 |
| 页面超时 / 空白 | 改等待策略，或切到浏览器观察真实状态 |

**失败是反馈，不是命令你原地重试。**

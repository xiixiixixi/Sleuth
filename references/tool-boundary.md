# 工具边界识别

Sleuth 不维护固定工具清单。每个运行环境里的内置工具、MCP 工具、专用连接器都可能不同。

Agent 的职责是先识别当前可用工具，再判断每个工具的证据边界，而不是默认套用某个工具。

## 运行时工具盘点

收到联网、调研、验证、查找、页面分析任务时，先在心智上完成一次工具盘点：

```text
我当前有哪些信息获取工具？
它们分别能发现什么、读取什么、验证什么？
它们看不到什么？
它们是否需要登录态？
它们是否可能产生状态变更？
它们的输出能否支撑核心结论？
```

常见工具族：

| 工具族 | 主要价值 | 证据边界 |
|---|---|---|
| 搜索发现类 | 找候选来源、别名、入口、关键词地图 | 排名和摘要有偏，不能单独支撑核心结论 |
| 页面读取类 | 快速读公开静态正文，降低 token 成本 | 不保证动态渲染、登录态、布局、展开内容真实可见 |
| 浏览器执行类 | 验证真实页面状态、登录态、站内搜索、动态内容、交互 | 成本高；默认只读；敏感页面谨慎截图和操作 |
| 专用连接器 | 读取 GitHub、邮件、日历、文件、数据库等结构化资源 | 只覆盖授权范围；要尊重工具返回的权限和时效边界 |
| 私有入口类 | 本地历史、书签、用户提供截图/录屏/文档 | 是线索或原料，不自动等于事实真实性 |
| 内容处理类 | PDF、图片、视频、字幕、表格、代码执行 | 需要标明提取方式；视觉/OCR/转录结果要保留不确定性 |

## 工具选择原则

先选最轻路径，证据不足再升级。

```text
公开、静态、权威页面 → reader/fetch 足够时不用浏览器
跨开放网络发现来源 → 搜索发现类优先
登录态、站内搜索、动态渲染、筛选排序、真实交互 → 浏览器验证
GitHub/邮件/日历/文件等结构化资源 → 专用连接器优先
高风险事实 → 原始来源优先，必要时多源交叉
```

## 浏览器升级条件

以下任一条件成立，应考虑升级到浏览器：

- reader 返回内容过短、空壳、导航页、登录提示
- 页面需要 JS 渲染、滚动、展开、筛选、排序
- 用户问的是某平台内、社区内、后台内、登录后可见内容
- 搜索结果全是摘要、镜像、转载，缺原始页面
- 站内搜索结果本身就是证据的一部分
- 需要确认页面真实状态、按钮、弹窗、价格表、图表或可见性

浏览器是高保真验证层，不是默认搜索入口。

## 人类可达但工具不可达的渠道

有些来源工具无法突破：

- 需要用户账号或组织权限的后台
- 私域社群、聊天群、封闭论坛
- 付费报告、预约 demo、人工销售回复
- 手机 App 内页面、评论深层分页
- 真实试用体验、访谈、线下观察

遇到这些渠道，不要伪造结论。应明确说：

```text
当前工具无法直接获取该渠道；需要用户提供截图、链接、导出文件、录屏、访谈记录或完成登录态。
拿到原料后，我可以整理、对比、提炼证据和形成判断。
```

## 输出时标注工具边界

关键结论需要能说明：

```text
这个结论来自哪个工具/来源？
它是一手事实、二手分析、用户反馈，还是模型推断？
这个工具有没有可能漏掉登录态、动态内容或最新变化？
还需要什么工具或人类材料来补齐？
```

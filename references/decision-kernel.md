# 搜索决策内核

本文不是 intent-router。不要把用户问题硬塞进固定任务模板。

Sleuth 要求 Agent 保持自主判断：每次搜索都用同一组决策问题控制路径、证据和停止条件。

## 核心原则

```text
先判断问题，再选择工具；
先识别来源，再设计 query；
先验证证据，再生成结论；
先暴露不确定性，再给行动建议。
```

## 九个决策问题

### 1. 用户真正要什么？

判断用户要的是：事实、解释、入口、方法、案例、比较、风险、评价、证据、决策依据、素材、原文，还是交付物。

不要把“查一下”默认理解成“给一堆链接”。

### 2. 这个事实会不会过期？

凡是涉及新闻、价格、政策、法规、软件版本、API、公司状态、人物职务、产品功能、排名、市场数据、推荐清单，都按可能过期处理。

可能过期，就需要当前来源和时间戳。

### 3. 这个问题最可能存在于哪类来源？

先想来源拓扑，再想关键词。

- 官方事实：官网、文档、公告、法规、价格页
- 实际体验：评论、论坛、社区、issue、视频教程
- 技术边界：docs、API、changelog、GitHub、release notes
- 市场判断：报告、财报、投资材料、数据库、新闻
- 登录态内容：站内搜索、后台页面、用户提供材料、浏览器验证

### 4. 当前有哪些工具最适合这个来源？

读取 `tool-boundary.md` 的工具盘点逻辑。

不要默认只用搜索引擎，也不要默认上浏览器。

### 5. 哪些结论必须回到原始来源？

关键结论必须能回答：

```text
Claim → Evidence → Source → Time → Confidence → Conflict
```

搜索摘要、SEO 文、单条评论、二手转载只能做线索，不能单独支撑核心结论。

### 6. 是否需要反证？

重要判断必须主动找：限制、失败、投诉、替代解释、旧数据冲突、定义差异、适用边界。

如果只找到支持性材料，结论要降置信度。

### 7. 是否需要升级到浏览器？

当 reader/search 无法验证真实状态，或内容依赖登录态、动态渲染、站内搜索、筛选排序、交互状态时，升级到浏览器。

浏览器是高保真验证层，不是默认入口。

### 8. 是否需要用户补充人类可达材料？

如果关键来源在封闭渠道、私域社群、登录后后台、付费内容、App 内、销售 demo、访谈或线下体验中，明确要求用户提供原料或完成登录态。

不要把不可达信息伪装成已验证事实。

### 9. 什么时候停止？

可以停止：

- 关键问题已答，证据足够支撑结论
- 新一轮搜索不再增加有效信息
- 剩余缺口不影响用户决策，并已明确披露

不能停止：

- 关键结论只有单一脆弱来源
- 存在明显冲突但未解释
- 重要数字没有来源或时间
- 只是流程跑完，但问题没有真正回答

## 输出要求

根据用户目标选择输出形态，但必须区分：

- 已验证事实
- 来源观点
- 高置信推断
- 未确认线索
- 冲突信息
- 覆盖缺口
- 行动建议

开放问题不要假装唯一答案。输出判断结构，而不是强行给单点结论。
